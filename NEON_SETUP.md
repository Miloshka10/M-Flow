# M-Flow: новая PostgreSQL в Neon вместо временной SQLite

Переход начинается **с чистой базы**, без переноса прежних тестовых аккаунтов
Render: пользователь подтвердил, что важных данных там нет, и согласовал этот
вариант. Локальная SQLite не удаляется. Роли, критерии оценивания, дизайн и
формы не меняются. Авторизация остаётся собственной авторизацией M-Flow;
Neon Auth и публичный Data API не подключаются.

## Текущий проект

Через подключение Neon подтверждён проект `M-Flow`, ID `old-base-68878782`,
организация `org-empty-block-74686072`, тариф `free_v3`, регион `aws-us-west-2`,
PostgreSQL 18. Это не подтверждает подключение рабочего сайта к этой базе:
для него ещё нужны закрытые переменные Render и согласованный запуск.
Не создавайте второй проект только ради строки подключения.

## Как выбирается база

- `M_FLOW_DATABASE_BACKEND=postgres` явно включает PostgreSQL.
- `DATABASE_URL` задаёт закрытую строку подключения приложения. Если backend
  не указан, наличие URL тоже выбирает PostgreSQL.
- `DATABASE_URL_UNPOOLED` — прямое подключение для создания/обновления схемы;
  для обычных запросов можно использовать pooled URL с `-pooler` в hostname.
  Если URL приложения уже прямой, второй URL можно не задавать.
- Для внешней базы требуется `sslmode=require`, `verify-ca` или `verify-full`.
  Используйте строку, которую выдаёт Neon, с её TLS-параметрами.
- Неверный URL, отсутствие URL при выбранном PostgreSQL или ошибка соединения
  **не** переключают приложение на SQLite и не создают замену базы.
- Без PostgreSQL-настроек локальный запуск остаётся SQLite. Тесты SQLite явно
  задают backend, чтобы случайно не обратиться к реальной внешней базе.

Приложение не читает `.env` автоматически. Настройки Render приходят из
Environment; для локального запуска переменные должны быть заданы процессу.
Никогда не пишите действующую строку подключения в README, Git, сообщения,
скриншоты, команды shell, логи или GitHub Actions.

## Подключение в Render после успешных проверок

Сначала убедитесь, что переход с чистой базы всё ещё приемлем. Старые тестовые
аккаунты в новом хранилище отсутствуют: ученики и учителя регистрируются заново.
Не пытайтесь загрузить `database.db` в Git для переноса.

1. В Neon откройте **Connect** у проекта `M-Flow`, выберите правильную базу и роль.
   Скопируйте pooled строку для приложения и direct строку для схемы. Не меняйте
   существующий пароль только ради получения строки.
2. В Render → Environment добавьте закрытые значения:

   | Имя | Значение |
   |---|---|
   | `M_FLOW_DATABASE_BACKEND` | `postgres` |
   | `DATABASE_URL` | pooled строка из Neon, с TLS |
   | `DATABASE_URL_UNPOOLED` | direct строка из Neon, с TLS |

3. `M_FLOW_SECRET_KEY` сохраните прежней. `M_FLOW_DEBUG` должен отсутствовать
   или быть `0`, чтобы не создавать демо-аккаунты. Если настроены
   `M_FLOW_TEACHER_USER`/`M_FLOW_TEACHER_PASSWORD`, они создадут начального учителя;
   для полностью пустой базы сначала самостоятельно уберите их в панели.
4. Root Directory — корень актуального приложения, не `M-Flow-main`.
   Build Command: `pip install -r requirements.txt`.
   Start Command: `gunicorn app:app`.
   Отдельная команда удаления/пересоздания базы не нужна.
5. Сохранение Environment может запускать деплой: делайте это только после
   проверки нового коммита и готовности запустить сайт с новой базой.
6. Выполните один согласованный деплой последнего проверенного коммита.
   Таблицы создаются в PostgreSQL транзакционно через direct соединение,
   без удаления существующих записей. Старт нескольких workers сериализован
   transaction-level advisory lock. SQLite не импортируется в PostgreSQL.

Коммит подготовки помечается `[skip render]`, чтобы обычный push не запустил
сайт со старыми переменными автоматически. Настройки панели агент не меняет.
Не объявляйте переход завершённым до настройки Environment и проверки сайта.

## Проверка реального сайта

После подключения пройдите на тестовых аккаунтах:

- регистрация/вход ученика и учителя, отдельные страницы ролей;
- создание проекта учеником, добавление учителя и участника;
- задача, ответственный, дедлайн, статус, отчёт;
- черновик → отправка → возврат → повторная отправка → принятие этапа;
- ссылка на видеозащиту и её проверка;
- черновая и опубликованная оценка: ученику видна только собственная публикация;
- закрытие вкладки и повторный вход.

Только потом отдельно согласуйте перезапуск/повторный деплой с проверкой,
что **те же** записи остались. Перезапуск Render не должен менять данные,
если сайт действительно использует внешнюю PostgreSQL. Условия Free, лимиты
и работоспособность подключения всё равно требуют наблюдения.

## Резервные копии PostgreSQL

`database_backup.py` предназначен **только для SQLite**. В режиме PostgreSQL
он отказывается выдавать копию старой локальной SQLite за копию рабочего сайта.
Для PostgreSQL используйте `pg_dump` с **direct** подключением. Версия клиента
должна поддерживать версию сервера (для PostgreSQL 18 используйте клиент 18+).
Pooled URL для dump/restore не используйте.

Пример шаблона команды, выполняемой владельцем на своём компьютере, с паролем
через интерактивный запрос, а не в аргументах команды:

```text
pg_dump --host=ПРЯМОЙ_ХОСТ_ИЗ_NEON --username=РОЛЬ_ИЗ_NEON --dbname=ИМЯ_БАЗЫ --password --format=custom --file=ПОЛНЫЙ_ПУТЬ_К_ЗАКРЫТОЙ_КОПИИ.dump
```

В окружении команды задайте `PGSSLMODE=require` (или строгий TLS-режим из Neon).
Храните файл в закрытой папке вне репозитория/публичного сайта, желательно
на другом устройстве с шифрованием. Копия содержит хеши паролей, закрытые
комментарии и оценки. Не публикуйте её в Git, чатах или Actions artifacts.
Независимые копии нужны даже при наличии Instant Restore: короткое окно истории
Neon не заменяет длительное хранение своих копий. Расписание не включалось.

Восстановление проверяйте на **отдельном локальном PostgreSQL-сервере**:
создайте новую пустую базу `mflow_restore_check`, затем выполните
`pg_restore --exit-on-error --no-owner --no-privileges --dbname=mflow_restore_check ПУТЬ_К_КОПИИ.dump`.
Не используйте имя/URL рабочей базы, `--clean` или перезапись поверх её таблиц.
Проверьте таблицы, записи и приложение на изолированной копии.
Восстановление production требует отдельного разрешения.

## Автоматические тесты

Общие тесты SQLite и адаптера запускаются локально без PostgreSQL. Полный
набор проверок ролей/CSRF также запускается на настоящем PostgreSQL 18 в
GitHub Actions; сервер создаётся только для CI, без доступа к Neon.

Для локального запуска этого набора нужен отдельный тестовый сервер и
`M_FLOW_TEST_POSTGRES_URL`: тесты принимают **только localhost/127.0.0.1/::1**
и базу `mflow_test`, создают случайную схему `mflow_test_<uuid>` и удаляют только
её. URL Neon/production отвергается. Проверяются повторный старт, все роли,
отчёты, этапы, защиты, оценки, права, CSRF, устаревшие формы и параллельная сдача.
Пропущенные без локального PostgreSQL тесты не выдаются за пройденные.
