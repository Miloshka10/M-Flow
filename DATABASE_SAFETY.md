Инструкция: [NEON_SETUP.md](NEON_SETUP.md). Аудит ниже описывает **прежний вариант

### Подтверждено кодом и локальными тестами

- `app.py` использует SQLite: `M_FLOW_DATABASE`, если задана, иначе
  `database.db` рядом с самим `app.py`. Относительное значение переменной
  разрешается относительно рабочего каталога процесса.
- Аккаунты (`users`), проекты (`projects`), участники (`project_members`),
  задачи (`tasks`), история отчётов (`task_updates`), этапы (`project_stages`),
  видеозащиты (`project_defenses`) и оценки (`project_assessments`) находятся
  в **одном файле**. В нём же профили навыков, приглашения и командные роли.
- Видео и презентации хранятся во внешних сервисах: копия базы сохраняет ссылки
  и результаты проверки, но не сами внешние файлы и не права доступа к ним.
- `prepare_database()` вызывается при импорте приложения. Таблицы/индексы
  создаются через `IF NOT EXISTS`; недостающие старые столбцы добавляются.
  Очистки таблиц, пересоздания базы или сброса результатов при старте нет.
  Повторный запуск на уже актуальной схеме сохраняет все записи и счётчики ID.
- `init_db.py` использует эту же инициализацию и тот же путь. Запуск приложения
  с **новым** путём создаёт новую пустую базу, а не переносит старую.
- Демо-аккаунты создаются только при `M_FLOW_DEBUG=1`. Мы не включали этот режим
  для рабочего сайта. Необязательный начальный учитель создаётся из переменных
  только при отсутствии логина; старые пароли и роли не перезаписываются.
- Рабочая база, `.env`, копии, WAL/journal-файлы не отслеживаются в текущем Git.
  `.gitignore` дополнен шаблонами приватных копий. Утилита также запрещает
  сохранять копии в проекте, любом обнаруженном Git-репозитории и известных
  публичных каталогах. `.gitignore` сам по себе не является контролем доступа.
- Найдены старые коммиты с `database.db`. Содержимое этих исторических файлов
  не читалось; они могут содержать старые данные. История Git не очищалась.
  Если там были настоящие пароли/данные, отдельно согласуйте очистку истории
  и смену скомпрометированных паролей. Не используйте GitHub как хранилище копий.
- В репозитории нет Render Blueprint (`render.yaml`), Dockerfile/Procfile
  или инструкции, автоматически подключающей диск. Дублирующий старый каталог
  `M-Flow-main/` не менялся: он не должен быть Root Directory для этого приложения.

### Сообщено пользователем, но не проверено в панели

- Free-тариф, отсутствие диска и `M_FLOW_DATABASE`.
- Build Command: `pip install -r requirements.txt` — установка зависимостей,

### Ещё требует панели Render

- Settings: правильная ветка/Root Directory, Start Command, Pre-deploy Command,

- `M_FLOW_DEBUG` должен быть выключен. Достаточно подтвердить это словами;

- После будущего согласованного переноса: фактический путь базы **внутри**
  mount path, проверенная копия вне сервиса и отдельно согласованная проверка
  сохранности тестовых записей при перезапуске. Само наличие диска недостаточно.

## Ограничение текущего бесплатного сервиса

По [документации Render](https://render.com/docs/free) Free не поддерживает
постоянные диски, Shell/SSH и one-off jobs, а локальные файлы теряются при
рестарте/деплое и остановке бесплатного экземпляра. Render может сам перезапустить
Free-сервис. Поэтому нельзя обещать сохранность даже без ручного деплоя.

Новая утилита в GitHub **не появляется в уже работающем экземпляре автоматически**:
для этого нужен деплой, который как раз может потерять текущую временную базу.
Не деплойте её ради выгрузки! В текущем приложении нет административного
экспорта всех данных. Нельзя выдавать доступ учителя к проектам за право скачивать
общую базу с паролями и чужими записями.

Если нет уже доступного канала экспорта, получение текущей полной базы на Free
остаётся блокером. Обратитесь в поддержку Render с вопросом, могут ли они
выгрузить SQLite из **текущего живого экземпляра без его замены**. Возможность
такой выгрузки не подтверждена. Не рассчитывайте, что смена тарифа или добавление
диска автоматически перенесут временные данные: изменение может вызвать рестарт.
До решения можно сохранить доступные через обычный интерфейс тексты/ссылки
в закрытые локальные файлы, но это **не** полноценная резервная копия.

## Инструмент резервного копирования

`database_backup.py` использует стандартную библиотеку Python и
[SQLite Online Backup API](https://www.sqlite.org/backup.html), а не копирование
открытого `.db` через `cp`/`Copy-Item`. Приложение импортировать не требуется;
инициализация и демо-данные не запускаются, отсутствующий источник не создаётся.
Снимок включает зафиксированные изменения WAL. Незавершённые транзакции не входят.
Записывать в рабочую базу, менять её настройки и делать checkpoint утилита не просит.

Снимок создаётся в закрытом временном файле, проверяется через `integrity_check`,
наличие всех обязательных таблиц и `foreign_key_check`, затем публикуется
без перезаписи существующего имени. Копируются и дополнительные таблицы,
индексы, SQLite sequence/user_version. Ошибки связей не исправляются автоматически.
При ошибке/таймауте копирования частичный результат не выдаётся за готовую копию.
Нужны свободное место и файловая система с поддержкой hard link; если их нет,
операция безопасно откажет. Проверка целостности может занять время сверх таймаута
самого копирования. После аварийного завершения процесса временный файл может
остаться в закрытом каталоге: это также пользовательские данные.

### Пример на компьютере (не текущий Render Free)

Создайте **закрытую** папку вне репозитория и любых папок, раздаваемых веб-сервером,
например `C:\Users\Miloshka\MFlow-private-backups`. На Windows проверьте ACL в
«Свойства → Безопасность»: только ваша учётная запись и системные администраторы,
без доступа других пользователей и без общего доступа. Unix-права `600` не
гарантируют аналогичный ACL в Windows. Имена ниже каждый раз должны быть новыми.

Из каталога проекта:

```powershell
python database_backup.py backup --output "C:\Users\Miloshka\MFlow-private-backups\mflow-20261009-01.sqlite3"
python database_backup.py verify --source "C:\Users\Miloshka\MFlow-private-backups\mflow-20261009-01.sqlite3"
python database_backup.py restore --source "C:\Users\Miloshka\MFlow-private-backups\mflow-20261009-01.sqlite3" --output "C:\Users\Miloshka\MFlow-private-backups\restore-check-20261009-01.sqlite3"
```

По умолчанию `backup` использует тот же путь, что приложение. Для другого
**существующего** источника передайте `--source "полный-путь.sqlite3"`, не меняя
`M_FLOW_DATABASE`. Локальная `database.db` — не база текущего Render и не её копия!
`verify` не выводит записи; `restore` не запускает сайт и восстанавливает только
в новый файл, запрещая существующий файл и путь настроенной рабочей базы.

### Пример на будущем сервисе с Shell и постоянным диском

Только после отдельно согласованного переноса и проверки реального пути:

```sh
mkdir -m 700 /var/data/private-backups
python database_backup.py backup --source /var/data/database.db --output /var/data/private-backups/mflow-20261009-01.sqlite3
python database_backup.py verify --source /var/data/private-backups/mflow-20261009-01.sqlite3
python database_backup.py restore --source /var/data/private-backups/mflow-20261009-01.sqlite3 --output /var/data/private-backups/restore-check-20261009-01.sqlite3
```

Это примеры **после** переноса, а не команды изменения текущей базы. Каталог на
POSIX должен иметь права `700`, файл получает `600`. `/var/data` должен быть реально
подключённым mount path; [постоянные диски Render](https://render.com/docs/disks)
недоступны в Build/Pre-deploy/one-off job. Копировать нужно из живого экземпляра,
не из отдельного ephemeral shell, у которого другая файловая система.

## Хранение и восстановление рабочей системы

Копия содержит логины, хеши паролей, оценки, закрытые комментарии и ссылки.
Не прикладывайте её к чату, issue, Actions artifacts и публичным облачным ссылкам.
Не выводите дампы, SQL или содержимое копии в логи. На защищённое другое устройство
переносите через согласованный приватный канал; при необходимости используйте
шифрование. Утилита **не шифрует** файлы и не организует облачное хранение.

Копия на том же диске не защищает от потери всего диска/аккаунта. Копия на временном
диске исчезнет вместе с источником. После важных изменений и перед будущими
деплоями делайте проверенную копию и храните хотя бы одну вне сервиса; расписание,
срок хранения и удаление старых копий согласуйте отдельно. В этой задаче расписание
не включалось и никакие существующие копии/пользовательские данные не удалялись.

Для реального восстановления потребуется отдельное разрешение: закрыть запись,
снять копию текущего состояния, восстановить выбранный снимок **в новый файл**,
проверить записи и права доступа на изолированной копии, и лишь затем согласовать
переключение приложения. Не копируйте `.db` поверх работающей базы и не удаляйте
её WAL/SHM. Данные после времени выбранного снимка в нём отсутствуют.
Этот инструмент намеренно не умеет перезаписывать рабочую базу.

## Безопасная публикация этого изменения

Итоговый коммит содержит `[skip render]`:
[Render документирует пропуск автодеплоя](https://render.com/docs/deploys#skipping-an-auto-deploy).
Старый workflow подключения темы также пропускает такие коммиты, чтобы не создать
следующий bot-коммит без этой метки. Новый workflow тестов только проверяет код,
не изменяет репозиторий и не запускает Render. Это не отключает Auto-Deploy навсегда:
следующий обычный push/ручной деплой снова опасен, пока база временная.

## Что проверяется автоматически

```sh
python -m unittest discover -s tests -p 'test_*.py'
```

Новые тесты используют исключительно временные базы с вымышленными данными:
повторная инициализация и старт нового процесса, все таблицы и метаданные,
резервная копия/восстановление, работа с WAL, commit другого соединения во время
копирования, отсутствие перезаписи, закрытые каталоги, отказ при повреждении,
таймаут, конфликт создания файла, отсутствие данных в выводе, Git ignore.
На Windows тест POSIX-прав пропускается, тест symlink требует дополнительных
прав и тоже может пропускаться. GitHub Actions на Linux запускает их отдельно
на Python 3.12 и 3.14. Успешные локальные тесты не подтверждают production,
доступность его текущей базы, работу Windows ACL или наличие внешней копии.
